# Architecture

DC Studio is a Rust core with a SwiftUI/AppKit shell. The split is not
incidental — it is the main structural decision in the project, and most of
the conventions below exist to keep the boundary between the two halves thin
and testable.

```
SwiftUI / AppKit           app/Studio        rendering, interaction, windows
      │
      │  UniFFI bindings   app/Generated     generated, not in git
      ▼
Rust core                  core/src          movegen, PGN, variation tree,
      │                                      SQLite, opening tree
      │
      ▼
UCI engine (Stockfish)     app/UCIKit        separate process, Swift-managed
```

**Everything correctness- or performance-sensitive lives in Rust**: legality,
PGN parsing and serialization, notation layout, the database. Swift renders
and handles input. The engine is the deliberate exception — UCI is a line
protocol over pipes, and process lifetime, cancellation, and back-pressure are
more naturally expressed in Swift, so `UCIKit` owns it.

## Rust modules

| Module | Responsibility |
|---|---|
| `position.rs` | Stateless functions over a FEN: `legal_moves_san`, `legal_moves_detailed`, `apply_san`, `start_fen`. Correctness pinned by perft tests. |
| `game.rs` | The `Game` object: variation tree in an arena (`Vec<Node>`, `children[0]` is the main line), PGN parsing and serialization, and every editing operation (`add_move`, `set_comment`, `add_nag`, `promote_variation`, `delete_node`). |
| `notation.rs` | `notation_tokens()` — flattens the tree into the token stream the notation panel renders. The contract is in [NOTATION-VIEW.md](NOTATION-VIEW.md). |
| `db.rs` | The `Database` object: streaming PGN import, paged and sorted game lists, substring search over White/Black/Event, opening-tree aggregation, write-back to `.pgn`. |

`cargo test` covers all of it (29 tests), including PGN round-trip fidelity —
the property everything else leans on.

## The FFI contract

Bindings are generated by [UniFFI](https://mozilla.github.io/uniffi-rs/) from
proc-macro attributes (`#[uniffi::export]`, `#[derive(uniffi::Object)]`, …).
There is no UDL file. After changing an exported signature, run
`scripts/build-core.sh`, which rebuilds the static library and regenerates
`app/Generated/dancechess_core.swift` plus its module map.

Three conventions matter:

- **No recursive structures cross the boundary.** Tree nodes are addressed by
  `u32` id (0 is the root); Swift receives flat `NodeInfo` records and asks for
  children by id. Ids stay stable across deletions — a removed subtree is
  unlinked, never compacted — so Swift can hold an id across an edit.
- **Stateful objects carry their own lock.** `Game` and `Database` wrap their
  interior state in a `Mutex` and are `Sendable` on the Swift side.
- **One error type.** `ChessError` (`InvalidFen`, `InvalidMove`, `Database`)
  surfaces in Swift as a thrown error.

## Game tree semantics

A node is one move. The root holds no move and represents the starting
position, which may be a custom FEN — that is how endgame studies and puzzle
positions enter the tree.

`add_move` validates against the position at the target node and normalizes
the SAN it stores (check and mate suffixes are filled in). Playing a move that
already exists under a node returns the existing node rather than duplicating
it; anything else is appended as a variation.

`fen_at(id)` replays the path from the root instead of caching positions.
Replaying a few hundred plies is far below perceptible, and the absence of a
cache removes a whole class of invalidation bugs.

## Data model: the PGN file is the source of truth

DC Studio does not own your games. Opening a `.pgn` imports it into a SQLite
cache under `Application Support/DCStudio/caches/`, one database per file,
keyed by the file's path. The cache is considered fresh when its modification
time is at or after every source file's — so edits made inside the app survive
across launches, while a `.pgn` modified by another program forces a rebuild.

Saving writes back to the `.pgn`: the whole file is re-serialized in id order
and swapped in atomically (write to a temporary file, then rename). The first
write to a given file in a session leaves a `.pgn.bak` beside it.

The trade-off is explicit: **saving normalizes formatting.** Moves, variations,
comments, and headers survive — that is what the round-trip tests protect —
but line breaks and spacing become ours.

### SQLite schema (WAL)

```sql
games(id, white, black, white_elo, black_elo, result, event, site,
      date, round, eco, ply_count, pgn)

positions(zobrist, game_id, move, result)      -- INDEX(zobrist)
```

- `games.pgn` holds the **re-serialized** game, not the original text. Storing
  one canonical form means there is exactly one parse path on the way back out.
- `positions` exists solely for the opening tree and the reference view; it is
  not a general position index (that was cut from scope). Each row is
  (zobrist of the position *before* the move, the move, the game's result), for
  the first 60 plies of each main line. Games starting from a non-standard FEN
  are not indexed. `result` is encoded 0/1/2/3 for white win, draw, black win,
  unknown; unknown games still occupy a `games` row but do not enter W/D/L.

Indexing by zobrist rather than by move sequence is what makes the reference
view transposition-aware: a position reached by a different move order matches.

Import performance on Apple Silicon (release build): a 100,000-game PGN
imports in about two seconds. Re-measure with
`cargo run --release --example import_bench -- <file.pgn>`.

## Engine integration

`EngineSession` (`app/Studio/Model/`) is a `@MainActor` loop around one
Stockfish subprocess: it issues `go infinite`, and when the position or MultiPV
count changes it sends `stop` and restarts. A generation counter discards
`info` lines that arrive after a target change. MultiPV defaults to 3.

Two behaviours are deliberate:

- **The engine only runs when a move is selected.** At the start of a standard
  game there is nothing to evaluate and no process is spawned. A game that
  starts from a custom FEN is the exception — its root *is* a position worth
  analyzing, so it is analyzed.
- **The subprocess starts lazily** and exits on stdin EOF, so quitting the app
  cleans up without signal handling.

The engine is looked up inside the app bundle first (`make-app.sh` embeds it),
then on the Homebrew path.

## The Swift side

- `app/Package.swift` is a SwiftPM harness that builds and runs the whole app
  with only the Command Line Tools. `app/project.yml` (XcodeGen) is optional
  and mirrors the same sources; code that must work in both uses
  `#if canImport(DanceChessCore)` / `#if SWIFT_PACKAGE`.
- The game list is an `NSTableView` behind `NSViewRepresentable`, paging 256
  rows at a time out of SQLite. SwiftUI's `Table` does not hold up at a hundred
  thousand rows.
- Keyboard handling goes through a local `NSEvent` monitor rather than
  SwiftUI's `.focusable()` + `onKeyPress`, which drops focus as soon as the
  board is clicked. See `KeyEventMonitor` in `GameWindow.swift`.
- Piece images are Merida SVGs kept as vector representations in `NSImage`, so
  they stay sharp at any board size.
